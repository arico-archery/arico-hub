# 03. スマレジ（POS）連携

> 読み取り連携が稼働中。店舗在庫の表示・在庫充当の判定に使用。
> 最終更新: 2026-08-11

---

## 1. 接続

- 秘密情報 `SMAREGI_CONTRACT_ID` / `CLIENT_ID` / `CLIENT_SECRET` は **Vercel 環境変数のみ**
- 同期した商品は `SmaregiProduct` テーブルに保存（`productCode`, `stock`, `stockTokyo`, `stockAichi`）
- 店舗は2つ（東京・愛知）

---

## 2. 商品コードの対応関係（確定事項）

**13桁のコード = JAN コード = 自社ECの受注オプションコード** の3つが一致する。
これが在庫を引き当てる鍵になっている。

- MakeShop の `variationCustomCode`（受注品目の `optionMemo` に保存）から数字13桁を取り出し、
  `SmaregiProduct.productCode` と突き合わせる（`src/lib/smaregi-option.ts` の `extractOptionCode`）
- 人が読めるオプション名（色・サイズ）もスマレジ側から解決して `OrderItem.optionLabel` に入れている

---

## 3. 在庫の引き当て方（3段階）

`/api/smaregi/stock-lookup`（POST）が受注登録画面などから呼ばれる。

1. **オプションコード** … 上記13桁での照合。最も確実
2. **バーコード** … カバー率が極端に低く実用にならない（カタログ848件中60件、FIVICS の変形は0件）
3. **名前 + オプション照合** … 実質これがメイン。スマレジ商品名の末尾からサイズ・色を剥がして
   基準名を作り、NFKC 正規化 + 括弧・空白除去して比較。`LEFT HANDED → lh` などの言い換え表も持つ。
   5分間のメモリキャッシュ（約14,800行）

> オプションを選んでいない状態では、その商品群の合計と SKU 数を `170(10)` のように表示する。

---

## 4. 既知の制約

### 原価が入っているのは全体の28%
スマレジ側に原価が登録されている商品が3割弱しかない。
そのため「スマレジを原価のマスターにする」案（B案）は**不採用**。
原価はカタログ経由で仕入先商品から取るのが正。

### マイナス在庫の正体
スマレジの在庫がマイナスになることがあるが、これは**請求書取引や手書き受注**で
POS を通さずに出荷した分。異常ではない。

### バックオーダー画面では在庫がほとんど見えない
バックオーダー一覧の在庫照合は**オプションコードのみ**を使っているため、
145件中8件しか照合できていない。受注登録画面が使っている「名前+オプション照合」を
バックオーダーにも適用すれば見えるようになる（→ `05-open-issues.md`）。

## 5. 将来構想（未着手）

**2レーン構成** — 在庫がある品目は「速いレーン」（発注を挟まず即発送）、無い品目は現行の
フルレーン（発注→入荷→発送）に分ける。在庫の唯一の正はスマレジに置く。
着手するなら「発送時の在庫引き落とし・引き当て」から。
