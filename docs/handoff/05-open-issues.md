## 🔴 進行中：SKU 3段連結

### これは何か

いま原価は「カタログ（商品群）→ 仕入先商品」の直結で決まっている。しかしカタログは商品群単位なので、
色や左右（RH/LH）まで指定して発注するには人が毎回バリエーションを選び直す必要がある。
その間に取り違えが起きていた（RH 注文なのに LH の商品に紐づいていた例が実際にあった）。

そこで**スマレジの SKU を間に挟む**構造を作っている。

```
カタログ（商品群）  ──1:N──▶  スマレジ SKU（オプション別）  ──1:1──▶  仕入先バリエーション
                                       ▲
                              受注のオプションコードと 99% 一致
```

これが埋まると、受注のオプションコードから**正確なバリエーション・原価・在庫**が自動で決まる。

### 大原則

- **仕入先バリエーションの確定は必ず人が行う。** 候補の提示と推奨表示は自動、確定のクリックは人。
  自動マッチングは 2026-07 に廃止済み（左右の誤マッチが致命的だったため）。同じ轍を踏まない。
- **カタログ → 仕入先の直結リンクは残しておく。** 候補を出す根拠であり、オプションコードのない受注
  （手書き受注など）のフォールバックでもある。消すと確定ボタン自体が出なくなる。
- 原価は引き続き仕入先商品から取る（スマレジの原価保有率は 28% しかないため）。

   リカーブの慣例（25インチハンドル基準 S=66" M=68" L=70"）で対応させる実装済みだが、
   **この対応が正しいか依頼者の確認待ち**。リムは間違えると返品が難しいので確認後に確定する。
2. **ARICO 20件・WJ 7件の一括確定** — KOREA・ANGEL・MK と同じ性格（色/サイズ別の仕入先商品が無い）。
   依頼者の判断待ち。
3. **MK X-ON ハンドル 3件の訂正** — SKU は 25" なのに 23インチのカタログに紐づいている（自動シードの誤連結）。
   カタログ側の連結から直す必要がある。※インチ不一致は一括確定でスキップするガードを入れてある。
4. **カタログが仕入先未マッチ 8件** — カタログのマッチングが先。
5. **カタログ未連結 194件** — `/sku-links` の「カタログ未連結」フィルタ →「カタログで探す」リンクから
   カタログ画面へ移動し、そこで SKU を付ける。
6. **残りの確定作業** — 販売数の多い順に進めるのが効率的。全部やる必要はない。
7. **第3段階の実装** — 受注取込がこのリンクを使うようにする。ここで初めて実効果が出る。
   リンクが無い SKU は現行方式にフォールバックするので、確定した分だけ正確になる。

**方針（2026-08-11 依頼者決定）: 今ある過去データを先に整理しない。** 稼働開始日を決めて、
その日の在庫を基準に一度で揃える。先に整理しても稼働日にはまた食い違うため。**日付は未定。**

1. **バックオーダーの在庫表示を拡張** — 現在バックオーダーの在庫照合はオプションコードのみで、
   145件中 8件しか照合できていない。受注登録画面が使っている「名前＋オプション照合」
   （`/api/smaregi/stock-lookup`）を適用すれば見えるようになる。
   ⚠ 名前照合は誤検出があり得るので**表示までに留め、自動充当はしないこと。**
2. **バックオーダーに「在庫で充当」ボタンを追加** — 現在 `stockAllocated` を立てられるのは
   受注登録と MakeShop 取込だけで、バックオーダー画面からは手を出せない。
   二重引き当て防止は `src/lib/stock-allocate.ts` の `availableByCode()` をそのまま使える。
3. **過去分の一括再判定** — 在庫充当は受注時点のスナップショット判定しか行わず、後から在庫が入っても
   再判定されない（機能自体が 2026-07-17 導入なので、それ以前の受注は判定すら受けていない）。

## 🟡 判断待ち（依頼者の決定が必要）

### 逆ざや 20件の整理
詳細は `04-data-history.md` §5。調査済みで、3つの選択肢を提示して保留中:
- **A案** SHIBUYA の1個単位商品にマッチングを変更（作業量小・副作用なし・**推奨**）
- **B案** 1個単位の商品を新規作成（下記の落とし穴あり）
- **C案** `packQty`（入数）フィールドを新設し原価を割る

> **B案の落とし穴（調査済み）**: 商品の手動作成は可能（`POST /api/products`）だが、
> ①`parse_jvd_excel.py` が取込開始時に JVD 商品を全て `out_of_stock` にしてから価格表にあるコードだけ
> 復活させるため、**手動商品は毎回品切れ扱いになり原価も更新されない**。
> ②発注書は `product.productCode` をそのまま印字するため、**偽のコードが仕入先向け発注書に載る**。

### オプションが可変の商品（7件）
重さ・サイズごとに売価も原価も違う商品（AXCEL スタビライザーウエイト等）。
カタログは1行1価格なので**カタログ画面の粗利表示だけが不正確**。受注時はバリエーションを選ぶので正しい。
対処案: 代表を最安バリエーションに合わせる／カタログ画面に原価の範囲を表示する。

### カタログ整理の残り約10%
依頼者の手作業が終わったら、遡及適用スクリプト（`_repoint-all.mjs`）を再実行すれば既存受注に反映される。
⚠ 遡及すると**過去月の損益が変わる**ので、実行前に必ず確認を取ること。
